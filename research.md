# Phase 2 Research

## System purpose and current behavior

The project evaluates whether memory-aware scheduling improves throughput and tail latency for multi-step LLM agents whose requests grow a retained KV cache across tool calls. Phase 1 replays scripted token-ID traces against `llama-server` and establishes FIFO baselines on an AWS NVIDIA T4 using Qwen3-0.6B Q8_0, a unified KV pool, and instrumented physical KV-cell metrics.

The current production path is request-level FIFO. Each ready model request enters one runnable FIFO; a worker removes the head, reserves an estimated prompt-plus-output token count for the request, calls `/completion`, appends generated tokens to that task's history, and either finishes the task or schedules its next request after the scripted tool delay. Tool waits release the inference worker while the task's cache can remain resident. The legacy task-level scheduler holds a worker through tool waits and is retained for comparison/tests.

The Phase 1 report selects request-FIFO with `N=4` and a 32K-cell pool as the main reliability/throughput baseline (roughly 94--96% completion and 4.21--4.30 completed tasks/min on the 500-task trace). `N=1` is the zero-failure reference. Higher concurrency fills the KV pool while GPU VRAM remains well below capacity, so Phase 2 should treat KV capacity and retained idle caches as the primary resource constraint.

## Architecture and data flow

1. `workloads/trace.py` defines the replay schema: a task has an ID, class, source, and ordered `Step`s. Each step contains token IDs to append, a fixed generation budget, and an optional tool delay.
2. `workloads/build_agenttrace.py`, `derive_agenttrace.py`, and `build_full_agenttrace.py` convert/source, scale delays, sample, and build the committed AgentTrace workloads. Arrival times are generated by `phase1.runner.run`, not stored in traces.
3. `phase1.runner.run` samples tasks and Poisson/burst offsets. `run_request_fifo` owns request admission, tool-return requeueing, deadlines, task state, and the current observational KV-fit diagnostic. `RunnableFifo` is a small condition-backed queue.
4. `harness.client.complete` streams a completion request and records prompt/cache/generated-token timing. `harness.server.Server` launches the configured `llama-server`; `ServerConfig` controls context/KV capacity, parallel slots, prompt cache, and batching.
5. `harness.kv_memory.KvMemSampler`, `harness.memory.GpuMemSampler`, and `harness.results.save`/the runner persist runtime measurements. Each run writes `tasks.csv`, `requests.csv`, `timeline.csv`, `admission_checks.csv` for request-FIFO, `kv_memory.csv`, `gpu_memory.csv`, `memory.csv`, and `meta.json`.
6. `analysis.metrics` and `analysis.reproduce_phase1` consume committed results without requiring a GPU. Existing tests use patched completion/server objects to validate scheduling semantics.

## Key files and reusable patterns

- `phase1/runner.py`: primary integration point; preserve `RunConfig`, `TaskRecord`, `RequestTaskState`, timeline accounting, deadlines, and result schema where possible.
- `harness/client.py`: use the existing completion interface and token accounting; do not introduce a second inference client.
- `harness/kv_memory.py` and `runtime/`: physical KV occupancy is available through the patched `/metrics` endpoint and has already been validated after slot erasure.
- `workloads/trace.py`: the canonical internal representation. External trace adapters should emit this representation rather than make the scheduler dataset-specific.
- `tests/test_phase1_scheduler.py`: established style for deterministic fake completions and focused async scheduler tests.
- `results/`: Phase 1 artifacts are committed; new development/evaluation outputs should be separated by group and retain provenance/configuration in `meta.json`.

## Phase 2 requirements inferred from the plan and writeup

The planned scheduler is a predictive two-queue policy. Ready requests remain in an age-ordered main queue. The scheduler estimates current request KV need from prompt length and output budget, estimates service time from Phase 1 measurements, reserves capacity for agents expected to return from tool waits, and may backfill a younger request only when the oldest request does not fit and the younger request's predicted runtime is within the oldest request's remaining wait allowance. Active generations are non-preemptive.

The policy also needs an aging threshold, bounded tool-return reserve, infeasible-request handling, and idle-cache eviction based on estimated reuse benefit per byte. Evicted tasks must be marked so their next request recomputes its prompt, and the implementation must verify that eviction actually reduces usable physical KV occupancy. Estimation errors, queue age, scheduler overhead, evictions, recomputation, and skipped/infeasible requests must be traceable in output data.

The project plan calls for an Exgentic adapter, separate development and held-out evaluation workloads, memory-aware FIFO first, then backfill/aging and cache eviction. Settings must be tuned only on development workloads and frozen before the held-out comparison against FIFO `N=4` and `N=1`.

## Constraints, risks, and open questions

- The writeup says prompt caching was enabled for the baseline while host cache was disabled in the main T4 runs; Phase 2 must preserve this policy or record an explicit, controlled deviation.
- The current estimated reservation is a simple `len(history) + n_gen`; it does not model allocator granularity, retained idle slots, or recomputation cost. Calibration should quantify bias and safety margin before admission is made authoritative.
- `llama-server` currently owns actual KV allocation. The Python scheduler can predict/admit, but cache eviction requires a supported server-side slot erase/reset mechanism or a narrowly scoped runtime extension. The existing validation demonstrates slot erasure, but the control path and request-to-slot mapping need to be confirmed.
- A tool-return reserve is a prediction problem: reserving too much reduces throughput, while reserving too little recreates context failures. It should be explicit in config and reported in results.
- Exgentic's exact source format, license/accessibility, tokenizer/model compatibility, and tool-result representation are not yet evidenced in this repository. The adapter should fail clearly when source data is unavailable and should produce a manifest with checksums and schema statistics.
- There is no static typecheck command in `pyproject.toml`; validation is currently `uv run pytest -q` plus the reproduction script. New code should remain compatible with Python 3.12 and add targeted tests rather than introducing an unconfigured type system.

## Recommended implementation surface

Keep the Phase 1 FIFO path stable and add a scheduler-policy layer or sibling runner that consumes the existing `RequestTaskState` objects. Add calibration/estimation utilities, a predictive scheduler implementation, eviction instrumentation/control, an Exgentic-to-trace adapter, development/evaluation workload manifests, result fields/tests, and analysis helpers. Avoid rewriting the client, server launcher, trace schema, or Phase 1 result readers unless a concrete Phase 2 metric requires an additive field.

## Adaptive-concurrency follow-up (2026-11-21)

The first slot-aware smoke run completed all 50 tasks but evicted 102 caches and recomputed 226,908 prompt tokens. The fixed dispatcher immediately reassigns an idle retained slot whenever runnable work exists, even when its owner is about to return from a short tool call. In the fixed 50-task AgentTrace workload, 40 of 63 tool waits complete within 500 ms; extending the cutoff to 1 s captures no additional waits. A 500 ms cache-preservation grace period is therefore the smallest useful adaptive-concurrency experiment.

The existing central dispatcher can implement this without changing llama.cpp: temporarily exclude grace-protected idle slots from eligible workers. The number of active requests then adapts between zero and four while protected owners wait. A returning owner can immediately reuse its slot; after the deadline the slot becomes eligible for the existing verified erase/reassignment path. Required additions are a configuration field, per-task grace deadlines, eligible-worker selection, an exact wakeup at grace expiry, result instrumentation, and focused scheduler/runner tests.

### Fairness follow-up

The 500 ms run recovered throughput to 3.359 tasks/min and reduced recomputation to 36,719 tokens, but completion p50 rose to 625.5 seconds and ready-queue p95 to 768.7 seconds. Median service time fell to 91.3 seconds, showing that the remaining regression is queue allocation rather than model execution. The immediate resume insertion lets multi-step tasks repeatedly move ahead of the original burst queue.

The smallest targeted correction is a weighted resume quota plus an old-head cutoff. One priority resume must be followed by one ordinary FIFO admission, and a FIFO head aged 30 seconds or more blocks priority. These controls should be separate from the cache grace itself: denied requests retain normal slot-aware semantics and can still obtain a cache hit when capacity permits. The experiment must measure actual cache reuse rather than merely returning before the grace deadline because a denied return can subsequently be evicted.

### Poisson follow-up

The fair-adaptive run showed that the 30-second cutoff removes nearly all adaptive-cache benefit on a burst workload. The next experiment returns to the previous unrestricted adaptive configuration (`cache_grace_s=0.5`, both fairness controls zero) without deleting the fair-policy implementation or results.

Phase 1's closest 50-task T4 comparison is N=4 with exponentially distributed arrivals at rate 0.2 tasks/s (mean interarrival 5 seconds), 32K KV cells, request-level scheduling, seed 2, host cache disabled, and prompt reuse enabled. Its historical FIFO run completed 46/50 tasks at 3.256 tasks/min and reported seven diagnostic backfill opportunities. The mean-10-second run reported only two opportunities, while the Phase 2 burst smoke reported none. Poisson-5 seconds is therefore the smallest matched smoke likely to exercise both queue variation and memory blocking.

A fresh two-arm run is preferable to comparing only against the historical artifact: FIFO and unrestricted adaptive should use the same current T4 runtime, trace, sampled task order, generated arrival gaps, model, deadlines, and instrumentation. Because each arm is expected to take roughly 14--18 minutes, the paired experiment should budget 35--45 minutes including model startup, download, and analysis.

The matched run confirmed the historical FIFO result (46/50, four KV failures, 3.255 tasks/min) and completed 50/50 adaptively at 3.454 tasks/min with no KV failures. Adaptive reduced prefill work by 30.7% and produced 38 actual grace hits, but completion p95 increased 22.2%. Poisson-5 seconds exposed seven FIFO diagnostic opportunities but zero eligible Phase 2 candidates: most blocked heads were already older than the aging threshold and had zero runtime allowance. The test also exposed and fixed two overlapping-return bugs: zero fairness now means truly unrestricted, and a request can be assigned only its retained slot or an unowned slot.

### One-resume/one-FIFO experiment

The next isolated variable is resume quota: `cache_grace_s=0.5`, `max_consecutive_resume_priorities=1`, and `resume_priority_head_age_limit_s=0`. Unlike the earlier fair-adaptive run, no 30-second resume cutoff is enabled. The quota should deny only consecutive priority returns when older FIFO work exists, allowing the next ordinary admission to reopen resume priority.

Run this policy on both existing smoke arrival patterns—50-task burst and matched Poisson-5 seconds—without rerunning FIFO. Compare against `smoke_phase1_fifo_n4_burst_50` and `smoke_phase1_fifo_n4_poisson5s_50`. This isolates whether quota alone recovers p50/p95 while retaining more KV reuse than the cutoff-dominated fair policy.

Both quota runs completed 50/50 tasks with zero KV failures. Relative to unrestricted adaptive, burst quota improved p50/p95 by 18.5%/6.8% at a 2.1% throughput cost; Poisson quota improved p50 4.2% but worsened p95 2.2% at a 4.1% throughput cost. Neither quota run beat plain FIFO latency, although FIFO failed four tasks in each workload. Quota is therefore most promising as a burst-sensitive fairness control rather than an always-on policy.

### Aging-threshold and cost-aware follow-up

The Poisson quota decision log shows blocked FIFO heads aged roughly 274--303 seconds. With the current 30-second aging threshold, their backfill allowance is already zero. Raising only the scheduler aging threshold to 360 seconds gives those observed heads about 49--78 seconds of guarded allowance and can admit many median-sized requests while preserving the one-resume/one-FIFO policy.

The second experiment replaces the fixed resume quota with a dynamic decision at a 30-second aging threshold. It should grant a within-grace resume only when estimated saved prefill time exceeds the delay cost imposed on queued FIFO work. This needs explicit benefit, cost, score, and denial-reason logging so any latency/cache-reuse tradeoff is attributable to the policy rather than inferred from aggregate results.

### Full R4 cost-aware evaluation

R4 is the strongest Phase 1 headline comparison for the cost-aware scheduler: N=4, Poisson mean 2-second arrivals, 32K unified KV, and 500 tasks. FIFO completed 472/500 at 4.26 tasks/min, reached 99.9% peak KV occupancy, and had p50/p95 completion of 3,984/5,420 seconds over successful tasks. This preserves the selected N=4 operating point while creating sustained memory and queue pressure.

The approved EC2 workspace is not a Git checkout, has no GitHub credential/deploy key, and has no IAM instance role. It can run independently and preserve results on its EBS volume, but cannot push to GitHub or invoke the EC2 StopInstances API without additional credentials. Passwordless OS shutdown is available; instance-initiated shutdown must only be used when its EC2 behavior is known to be stop rather than terminate.

The unattended supervisor pattern was validated by the full R4 run: launch with `nohup`, stream a dedicated supervisor log, archive the output group, call `sync`, and schedule `sudo shutdown -h +1` only after the benchmark and archive complete. The instance stopped rather than terminating and retained its EBS artifacts across restart. Reuse this pattern for later long runs on this instance.

### Full R5 aging comparison

Phase 1 R5 uses 500 tasks, N=16, Poisson mean 2-second arrivals, and a 32K unified KV pool. FIFO completed only 100/500 tasks at 5.55 completed tasks/min; its p50/p95 of 127/270 seconds are strongly survivor-biased. The matched Phase 2 experiment compares cost-aware aging thresholds 30 and 360 on separate T4 instances while holding trace, seed, runtime, model, KV pool, cache grace, cost weight, and all other scheduler settings fixed.

The age-30 host reuses the validated R4 workspace. The age-360 host has the same instrumented llama.cpp binary and model but only 1.1 GB free, so it requires a minimal source-only workspace using its existing Python virtual environment. Both runs use the validated detached archive, sync, and one-minute shutdown sequence.

Both R5 policies completed 500/500 tasks with zero KV-context failures. Raising aging from 30 to 360 increased backfills from 38 to 135, reduced average queue length from 222.0 to 207.0, and improved p50/p95 by 4.5%/1.8%. It also reduced cache-hit ratio from 45.8% to 44.1% and increased recomputed prompt tokens 4.8%, explaining why the large increase in backfill produced only modest end-to-end gains.

### Physical-reconciled admission follow-up

The current logical calculation already subtracts a returning task's retained idle cache before adding its full predicted footprint, so merely subtracting the resident prefix again would be unsafe double-subtraction. Output-budget calibration also offers no gain on this trace: all 1,068 requests in each full run generated exactly their requested token budget.

The actual opportunity is reconciliation with fresh physical occupancy. In R5 age 30, 3,013 of 3,471 blocked decisions occurred below 80% measured KV use and 2,089 occurred below 70%; median physical occupancy at a block was 67.2%. A safe physical-reconciled projection starts from a fresh synchronous physical sample, then adds worst-case remaining incremental growth for active requests, incremental growth for the candidate, tool-return reserve, and the existing safety margin. A retained prefix is recognized only when explicit slot ownership and resident-cell accounting agree. Missing or stale physical data must fall back to the current logical projection.

The matched smoke rejected the initial conservative physical formula. It completed 50/50 safely with zero sampling fallbacks, but throughput fell 9.6%, p50/p95 increased 35.9%/15.4%, blocked-head decisions rose from 21 to 96, and mean KV fell from 54.8% to 51.6%. The physical baseline already contains partially materialized active growth; adding each active request's original full growth reserve double-counts that portion. The implementation was reverted after preserving its artifacts. Physical admission requires per-slot remaining-progress telemetry or a calibrated remaining-growth bound before it can outperform logical accounting safely.
## Two-queue implementation findings

- `RunnableFifo.take()` removes work before admission is decided, and each Phase 1 worker independently computes its diagnostic reservation. A predictive policy cannot safely reuse that control flow: two workers could observe the same capacity and both admit. Phase 2 therefore needs one condition-backed dispatcher that owns queue selection and active reservations atomically, while request execution remains concurrent in separate jobs.
- The backfill queue should not become a second owner of requests. The main queue remains authoritative and ordered by the original request-ready timestamp; the backfill queue is a computed list of currently eligible younger entries. This prevents duplicate state and preserves age when a request is reconsidered.
- `complete()` already supports an explicit `id_slot` and reports the actual slot in its final response. Phase 1 passes `-1`, allowing the server to choose. Reliable targeted eviction requires explicit slot ownership or another verified task-to-slot mapping; otherwise the scheduler cannot know which idle task `/slots/<id>?action=erase` will remove.
- The physical KV sampler runs in a background thread at one-second intervals. It is suitable for run-level measurement but too stale for admission. Phase 2 should make admission from deterministic reservations and use synchronous physical samples for validation/eviction confirmation, unless the runtime instrumentation is extended to expose a safe low-latency control signal.
- Full prompt length is not the same as incremental KV demand when a prefix remains resident. The conservative first policy can reserve the complete `len(history) + n_gen`, but it will underutilize the pool. A later calibrated estimator can subtract verified reusable prefix cells; the decision log must identify which model was used.
- The existing request records contain `prompt_n`, `cache_n`, `prompt_ms`, `predicted_n`, `predicted_ms`, TTFT, and TPOT. These support an offline runtime estimator without adding inference calls. The development split must be used for fitting and the estimator artifact/configuration must be frozen before held-out evaluation.
- Tool delays are scripted in the replay trace. Using exact remaining delay would give the scheduler oracle knowledge. The implementation should distinguish an oracle diagnostic from the primary deployable policy, which should use only elapsed wait and a model/historical estimate available at decision time.
- A request larger than the total pool is not necessarily infeasible if it has a reusable resident prefix. The infeasibility rule must use the same conservative/incremental accounting model as admission and should be evaluated when the pool is otherwise idle.


Recommended order
1. Implement adaptive concurrency with a short cache-preservation grace period.
2. Add eviction, recomputation, and slot-idle-time measurements.
3. Benchmark llama.cpp slot save/restore versus recomputing contexts at 2K, 4K, 8K, and 16K tokens.
4. If host-memory restore is faster, implement a small InferCept-style CPU KV tier.
5. Add cost-based selection among preserve, swap, and discard.
6. Repeat the same 50-task AgentTrace smoke test.
